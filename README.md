# 렛츠런플레이 통합 예약·결제 프로토타입

서울 렛츠런파크의 포니 타기·포니랑 놀기 예약 흐름과 통합 운영 관리자, 위이 내부 계정 관리를 검토하기 위한 프론트엔드 프로토타입입니다. 실제 로그인·결제·서버 예약 시스템이 아니며 운영 데이터는 브라우저 저장소에만 보관됩니다.

이 README는 저장소에 있는 요구사항·기능 명세·개발 검토·프론트엔드 전달 문서를 한눈에 찾고, 서로 다른 문서의 상태를 구분하기 위한 문서 허브입니다.

## 화면 내 개발 정책 보기

예약 화면, 운영 관리자, 위이 계정 관리 화면에서 `Alt + P`를 누르면 현재 화면의 정책 영역이 표시됩니다. 헤더에는 별도 정책서 버튼을 노출하지 않습니다.

- `P` 표시가 붙은 화면 영역을 클릭하면 해당 정책 상세가 열립니다.
- 하나의 정책 안에서 서비스 운영 기준 → FE 화면 동작 → BE 서버 검증을 함께 비교합니다.
- `결정 필요`는 승인 전 항목이며 구현 확정값으로 사용하지 않습니다.
- `Esc`는 상세 → 목록 → 정책 보기 종료 순서로 동작합니다.

| 화면 | 정책 키 | 범위 |
| --- | --- | --- |
| 예약 | RSV-01~RSV-07 | 로그인, 프로그램·날짜, 회차 충돌, 인원·할인, 장바구니, 결제, 티켓·취소·입장 |
| 운영 관리자 | ADM-01~ADM-08 | 예약 권한, 프로그램, 회차, 할인, 부분환불, 운영 취소, 정산, 보안 |
| 위이 계정 관리 | ACC-01~ACC-04 | 계정 조회, 발급·재설정, 기능 권한, 중지·보안·감사 |

정책 데이터의 구현 기준은 [developer-policy.js](developer-policy.js)입니다. 서비스 정책은 고객·운영 관점의 기준과 확정 내용을, FE는 클릭·표시 동작을, BE는 API 검증·저장·예외 처리를 설명합니다. 화면별 정책은 해당 영역에만 연결하고, 서버 정책만 있는 항목은 FE가 비어 있음을 명시합니다.

## 확정된 핵심 정책

### 회원과 계정

- 네이버·카카오 간편로그인을 제공하고 비회원 예약은 허용하지 않습니다.
- 로그인 제공자가 다르면 별도 회원으로 식별합니다. 동일인 계정 연결은 아직 미확정입니다.
- 서울·부산경남·제주는 통합 회원 체계를 사용합니다.
- 장바구니와 예약 조회는 인증된 회원 기준으로 분리합니다. 클라이언트가 보낸 회원 ID를 권한 판단에 사용하지 않습니다.
- 관리자 계정은 부서별 공용 계정 1개와 별도 통합 관리자 계정으로 구성합니다.

### 프로그램과 회차

- `프로그램 → 반복 회차 템플릿 → 날짜별 실제 회차` 구조로 관리합니다.
- 프로그램에는 지역·부서·유형·명칭·가격·운영/노출/판매 기간·요일·취소 마감·할인·정산/한도/충돌 그룹을 둡니다.
- 회차에는 시작·종료 시각, 온라인 판매 수량과 판매 상태를 둡니다. 회차명은 시간순으로 자동 생성합니다.
- 키오스크와 API로 연동하지 않으며 현장 수량과 온라인 수량을 분리합니다.
- 프로그램·회차·가격·할인을 변경해도 기존 주문은 결제 당시 스냅샷을 유지합니다.

### 예약과 장바구니

- 현재 화면은 포니 타기와 포니랑 놀기 두 상품을 제공합니다. 통합 구축 범위가 두 상품으로 한정된다는 뜻은 아닙니다.
- 예약 가능 이용일은 판매 기간 안에서 오늘 기준 향후 14일까지입니다.
- 같은 계정의 확정 예약과 장바구니를 합쳐 이용 시간이 일부라도 겹치면 차단합니다.
- 시간은 `[시작, 종료)` 구간으로 비교해 앞 회차 종료와 다음 회차 시작이 같으면 허용합니다. 레거시 투어는 80분을 적용합니다.
- 포니 프로그램의 구매 한도는 계정별 **이용일 하루 합산 최대 4매**입니다.
- 장바구니에는 하나의 이용일만 담을 수 있습니다. 장바구니 보관만으로 정원을 확정하지 않습니다.
- 사용자 취소 마감의 기본값은 이용 시작 10분 전이며, 프로그램별 예외값과 사용자 직접 부분취소 범위는 별도로 확정합니다.
- 담기·수량 변경·주문 진입·결제 직전에 최신 조건을 다시 검사합니다.

### 할인

- 과천시민 할인은 50%이며 두 포니 프로그램을 합쳐 계정별 **이용일 하루 최대 2매**입니다.
- 온라인에서 할인된 금액을 결제하고 현장에서 증빙합니다. 증빙 실패 처리는 미확정입니다.
- MVP에서는 티켓 하나에 할인 하나만 적용하며 중복 할인은 허용하지 않습니다.
- 정률·정액, 1매당 상한, 적용 수량·기간·프로그램·증빙·사용량 복원 여부를 정책 데이터로 관리합니다.
- 할인 비활성화나 변경은 신규 예약에만 반영하고 과거 결제 내역은 바꾸지 않습니다.

### 주문·결제·티켓·환불

- 여러 예약 항목을 하나의 주문으로 결제할 수 있으며 주문·예약·티켓·결제·환불 식별자를 분리합니다.
- 사용자에게는 같은 상품·이용일·회차의 인원을 묶은 티켓을, 관리자에게는 인원별 개별 티켓을 표시합니다.
- 결제 전 서버가 회원·가격·할인·재고·구매 한도·시간 충돌을 잠금 상태에서 재검증해야 합니다.
- PG 승인 검증 후 재고 차감·주문 확정·티켓 발급·할인 사용량을 하나의 트랜잭션으로 처리합니다.
- 중복 요청, 늦은 응답, 웹훅 중복, PG 승인 후 DB 저장 실패를 조회·재처리할 수 있어야 합니다.
- 부분취소는 선택 티켓의 실제 배분 결제액만 환불하고 나머지 인원과 예약을 유지합니다.
- 환불 결과가 불명확하면 완료로 표시하지 않고 `확인 필요` 상태로 둡니다.

### 관리자·정산·운영

- 다른 부서의 프로그램은 조회할 수 있지만 수정·예약 처리·환불·정산은 권한이 있는 자기 부서 데이터로 제한합니다.
- FE에서 메뉴나 버튼을 숨기는 것과 별개로 모든 API에서 부서·기능 권한을 재검증합니다.
- 비밀번호는 단방향 해시로 저장하고 원문을 다시 표시하지 않습니다. 분실 시 새 임시 비밀번호만 발급합니다.
- 계정 사용 중지는 기존 로그인 세션에도 적용하고, 변경 전후 값·사유·처리 계정·시각을 감사 로그에 남깁니다.
- 정산은 서비스 제공 완료일 기준으로 지역·부서·프로그램별 결제액·환불액·PG 수수료·지급 예정액을 구분합니다.
- 서버·DB·신규 도메인은 위이에서 구축·운영하며 운영 환경에는 접근 통제, 백업·복구, 모니터링과 개인정보 보호가 필요합니다.

- P-03: 나눠 입장·사용 취소·할인 증빙 실패·노쇼를 어떻게 처리할지
- P-04: 판매된 회차·정원·정책 변경과 PG 전환 전 주문을 어떻게 처리할지

정책 확정 시 `정책 ID / 질문 / 승인값 / 승인 담당 / 승인일 / 적용 시작일 / 기존 예약 처리 / 관련 화면·API / 검수 사례`를 함께 기록합니다.

## 주요 검수 기준

- 다른 회원이 마지막 한 자리를 동시에 결제해도 초과 판매하지 않아야 합니다.
- 같은 회원이 여러 기기에서 겹치는 시간을 동시에 결제해도 하나만 확정되어야 합니다.
- 장바구니 일부 마감·가격 변경 시 사용자 동의 없이 구성이나 금액을 바꾸면 안 됩니다.
- 결제창 닫기·응답 지연·중복 통지 후에도 결제와 예약 상태를 조회로 복구할 수 있어야 합니다.
- 여러 번 부분환불해도 환불 누계가 원 승인금액을 넘지 않고 정산 자료와 일치해야 합니다.
- 타 예약번호·부서로 요청값을 바꿔도 개인정보·취소·다운로드 권한을 넘을 수 없어야 합니다.
- 정책·가격·회차 변경 후에도 과거 주문은 구매 당시 값을 유지해야 합니다.
- 자동 테스트 통과와 실제 로그인·PG·권한·동시성 통합 검수 완료를 구분해야 합니다.

기능명세의 전체 검수 시나리오는 AT-01~AT-14, 개발 검토의 확장 시나리오는 X-01~X-12를 참고합니다.

## 로컬 실행과 테스트

별도 빌드 없이 `index.html`을 열어 확인할 수 있습니다. 로컬 서버가 필요하면 저장소 루트에서 실행합니다.

```sh
python3 -m http.server 4173
```

전체 자동 테스트:

```sh
node --test tests/*.test.cjs
```

테스트는 브라우저 프로토타입의 시간 충돌, 계정 구분, 할인·금액, 장바구니, 회차별 티켓과 정책 연결을 검사합니다. 운영 서버의 보안·동시성·PG 성공을 보장하지는 않습니다.

## 공개 파일 갱신

원본 HTML·CSS·JavaScript 또는 이미지를 수정한 뒤 다음 명령으로 공개용 파일을 갱신합니다.

```sh
node scripts/build-pages.mjs
```

생성된 `docs/`를 함께 커밋해 `master` 브랜치에 푸시하면 GitHub Pages가 배포됩니다. `docs/`는 허용된 화면·스크립트·스타일·이미지만 포함하며 저장소 내부 문서는 게시하지 않습니다.

## 운영 전 필수 주의

실서비스에서는 브라우저의 회원 ID, 가격, 할인, 예약 상태를 신뢰하면 안 됩니다. 인증된 서버 회원 ID, 원자적 재고 차감, PG 승인 검증, 멱등성, 서버 권한 검사, 개인정보 보호, 감사 로그, 백업·복구와 장애 모니터링을 별도로 구현해야 합니다.
