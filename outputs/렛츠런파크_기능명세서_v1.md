# 렛츠런파크 통합 예약·결제 시스템
기능 명세서 v1.0 · 회의 및 후속 논의 반영본

작성 기준일: 2026. 08. 28. | 문서 상태: 협의용 초안
검토 대상: 한국마사회 담당부서 · 주식회사 위이 기획/개발 담당

## 01. 문서 목적과 적용 범위
본 문서는 회의 원문, 후속 대화에서 정한 기능, 견적서 v7의 주요 기능 범위를 대조하여 사용자·관리자 기능과 검수 기준을 정리한 문서입니다. 금액과 계약 조건은 견적서를 따르며, 이 문서는 세부 기능 협의를 위한 기준안입니다.

### 이번에 반영한 핵심 결정
- 사용자 화면은 **포니 타기 / 포니랑 놀기** 두 상품을 중심으로 구성합니다.
- **상품 목록 → 상품 상세·옵션 선택 → 장바구니 → 주문·결제 → 예약 완료·티켓** 순서로 이용합니다.
- 중복 예약은 참석자별이 아니라 **예약 회원 계정의 이용 시간**을 기준으로 검사합니다.
- 사용자는 **상품·이용일·회차별 묶음 티켓**, 관리자는 **인원 1명당 개별 티켓**을 확인합니다.
- 개별 인원 또는 일부 예약을 취소하고 **부분환불**할 수 있도록 설계합니다.

### 현재 화면과 통합 구축 범위의 구분
현재 화면의 상품을 두 개로 정리한 것은 사용자 흐름과 시연 대상의 결정입니다. 통합 회원과 지역·부서·프로그램 관리 구조를 두 상품으로 축소한다는 의미는 아닙니다. 견적서의 초기 6개 프로그램·21개 CTA 전제와 실제 오픈 대상은 별도로 대조하여 확정합니다.

### 문서의 상태 표기
**반영**은 회의의 확정 방향 또는 후속 요청을 명세에 반영했다는 뜻이며, 개발·검수 완료를 뜻하지 않습니다. **협의**는 기능의 세부 정책을 정해야 하는 항목입니다. **설계안**은 요구 기능을 일관되게 구현하기 위한 제안으로, 승인 후 적용합니다. 실제 구현 현황은 제13장에서 따로 표시합니다.

## 02. 회의 내용 업데이트
회의 원문의 ‘검토 필요’ 상태 중 아래 항목은 후속 논의를 기준으로 갱신합니다. 원문 자체를 수정하거나 과거 논의가 처음부터 확정이었던 것으로 표시하지 않습니다.

| 항목 | 회의 당시 | 이번 명세 반영 내용 |
| --- | --- | --- |
| 장바구니·일괄결제 | 개발팀 검토 | 여러 상품·날짜·회차를 담아 한 번에 결제하는 기능 반영 |
| 사용자 티켓 | 인원별/프로그램별 분리 검토 | 상품·이용일·회차가 같은 예약 인원은 한 티켓으로 표시 |
| 관리자 티켓 | 분리 단위 검토 | 예약 인원 1명당 티켓 1개를 관리하고 개별 취소 |
| 부분취소·부분환불 | 정책·개발 검토 | 기능 반영. 할인 배분, 수수료, 사용자 직접 부분취소 범위는 협의 |
| 중복 예약 주체 | 동시 이용 불가 프로그램 제한 | 참석자 정보가 아닌 예약 회원 계정 기준으로 검사 |
| 시간 비교 방식 | 같은 시간대 제한 | 시작 시각뿐 아니라 시작~종료 구간의 일부 겹침도 차단 |
| 사용자 구매 흐름 | 날짜 중심 예약 화면 | 두 상품의 목록·상세·장바구니·주문 화면을 분리한 커머스 구조 |

### 회의에서 유지하는 방향
- 서울·부산경남·제주는 통합 회원으로 운영하고 네이버·카카오 로그인을 제공합니다.
- 기존 키오스크와 API 연동하지 않으며, 온라인 판매 수량은 별도 관리합니다.
- 관리자 구조는 지역 → 부서 → 프로그램이며, 다른 부서 조회와 소속 부서 수정 권한을 구분합니다.
- 프로그램별 예약 기간·회차·온라인 판매 수량·할인·취소 가능 시간을 설정합니다.
- 초기 위이 PG 활용을 우선하되 장기 PG 구조·정산일·세금계산서 처리는 협의합니다.

## 03. 회원·상품·예약 옵션
상품 목록은 비로그인 상태에서도 볼 수 있습니다. 계정별 장바구니와 예약 내역은 로그인 후 이용합니다.

### USR-01. 통합 회원과 간편 로그인 [반영]
**동작:** 네이버·카카오로 로그인하고 통합 회원 체계에서 지역별 예약을 관리합니다. 마사회 소유 앱에 위이 개발 권한을 부여해 연동합니다.
**확인:** 본인 예약만 조회합니다. 동일인의 네이버·카카오 계정을 합칠지는 D-09에서 정합니다.

### USR-02. 상품 목록 및 상세 진입 [반영]
**동작:** 두 상품을 별도 카드로 표시하고 이름·이미지·가격·대상을 안내합니다. 상세에서 옵션을 선택하며 기존 콘텐츠의 예약 CTA도 서비스로 연결합니다.
**확인:** 투어는 현재 두 상품 목록에 표시하지 않습니다. 향후 지역·프로그램 오픈은 별도 대상 목록에 따릅니다.

### USR-03. 날짜·회차 선택 [반영]
**동작:** 운영일과 예약 가능 기간 안의 날짜만 선택할 수 있습니다. 선택한 날짜에 판매 가능한 회차, 잔여 수량, 마감·중복 상태를 표시합니다.
**확인:** 날짜·회차는 직접 선택합니다. 선택한 회차가 불가능해지면 다른 회차로 자동 변경하지 않고 재선택을 요청합니다.

### USR-04. 인원·할인 선택 [반영 / 값 협의]
**동작:** 허용 인원·잔여 수량 안에서 인원과 할인을 선택합니다. 옵션 변경 시 금액을 다시 계산합니다.
**확인:** 할인 대상·중복 적용·증빙·최대 수량은 정책으로 관리합니다. 현재 화면의 가격과 수량은 제10장 D-01에서 확인합니다.

### USR-05. 예약 조회와 마이페이지 [반영]
**동작:** 본인의 주문·예약·티켓·결제·환불 내역과 상품·일정·인원을 확인합니다. 취소 가능 여부와 처리 상태를 표시합니다.
**확인:** 화면 표시 건수와 무관하게 중복 검사는 계정의 유효 예약 전체를 대상으로 합니다.

## 04. 중복 예약 규칙과 장바구니
### RSV-01. 예약 회원 기준 시간 중복 검사 [반영]
**기준:** 상품 종류와 예약 인원 수에 관계없이, 동일 회원의 기존 유효 예약 및 장바구니 항목과 이용 구간이 겹치면 추가 예약을 막습니다. 참석자 이름을 따로 받는지와 무관합니다.
**판정:** 시작 A < 종료 B 이고 시작 B < 종료 A 이면 중복입니다. 다른 날짜는 별도이며, 취소 완료된 인원만 제외합니다. 아직 유효한 인원이 남은 예약은 계속 시간을 점유합니다.

### RSV-02. 검사 범위와 시점 [반영 / 일부 협의]
**동작:** 장바구니 담기, 주문 진입, 결제 확정 시 최신 예약과 다시 비교합니다. 실제 서비스는 인증된 회원 ID를 기준으로 서버에서도 동일 검사를 수행해야 합니다.
**협의:** 지역 간 적용 범위와 이동·준비시간은 D-02에서 확정합니다. 현재 화면은 종료 시각과 다음 시작 시각이 같으면 허용합니다.

### CART-01. 상품·회차별 담기 [반영]
**동작:** 선택 상품·이용일·회차·인원·할인을 하나의 장바구니 항목으로 저장합니다. 담기 성공 후 ‘쇼핑 계속하기 / 장바구니 보기’를 제공합니다.
**확인:** 같은 회차를 다시 별도 항목으로 담을 수 없으며, 인원 변경은 기존 항목에서 합니다. 실패 시 기존 항목과 금액을 임의로 변경하지 않습니다.

### CART-02. 별도 장바구니 화면 [반영]
**동작:** 상품별 선택 옵션, 인원 수정·삭제, 상품 금액·할인 금액·총 결제 예정 금액을 제공합니다. 계정별로 분리하며 결제 완료된 항목은 비웁니다.
**확인:** 장바구니는 예약 확정이 아닙니다. 저장 기간, 정원 점유 여부와 결제 대기 시간은 D-06에서 정합니다.

## 05. 주문·결제와 티켓
### ORD-01. 장바구니 일괄 주문 [반영]
**동작:** 장바구니의 여러 항목을 하나의 주문으로 결제합니다. 주문 화면에서는 상품·옵션·예약 계정·최종 금액을 확인하고, 수정은 장바구니로 돌아가 진행합니다.
**확인:** 금액·일정이 바뀌면 재확인과 동의를 받습니다. 가격·할인·회차·정원을 서버 기준으로 검증합니다.

### ORD-02. PG 결제와 결제 결과 처리 [반영 / 연동 협의]
**동작:** 초기 위이 PG 사용 방향으로 결제·전체환불·부분환불을 연결합니다. 계좌이체는 제공하지 않으며, 나머지 수단은 계약·연동 범위에서 확정합니다.
**확인:** PG 승인 확인 전 예약을 완료로 표시하지 않습니다. 실패·사용자 이탈·중복 요청·응답 지연 시 중복 청구나 중복 예약이 생기지 않아야 합니다.

### TKT-01. 사용자 묶음 티켓 [반영]
**단위:** 동일 주문 내 **상품·이용일·회차별 예약**마다 한 장을 표시합니다. 같은 회차 3명은 사용자 티켓 1장에 총 3명으로 표시하고, 다른 상품이나 회차는 별도 티켓으로 표시합니다.
**확인:** 주문번호와 회차별 예약번호를 연결하고, 티켓에서 일정·상품·유효 인원·할인 여부를 확인합니다.

### TKT-02. 관리자 인원별 티켓 [반영]
**단위:** 사용자 묶음 티켓 아래에 예약 인원 수만큼 개별 티켓을 생성합니다. 3명 예약이면 관리자 티켓 3개이며, 각각 상태·취소·환불 이력을 구분합니다.
**확인:** 인원별 관리가 참석자 실명 수집을 뜻하지는 않습니다. 번호로 구분할지, 별도 인적 정보를 받을지는 D-05에서 결정합니다.

### TKT-03. 입장 상태와 직원 확인 [반영 / 값 협의]
**동작:** 입장 대기·입장 가능·입장 종료를 구분하고, 입장 가능한 티켓에는 움직이는 표현 등을 적용합니다. 할인 증빙 확인 문구와 실제 유효 인원을 표시합니다.
**확인:** 취소 상태는 시간상 입장 가능 상태보다 우선합니다. 실제 입장 처리·중복 입장 방지 방식과 시간 기준은 D-05에서 정합니다.

## 06. 전체·부분취소와 환불
### CAN-01. 사용자 예약 취소 [반영 / 범위 협의]
**동작:** 본인 예약에서 취소 대상과 환불 예정 금액을 확인하고 취소합니다. 상품별 사용자 취소 가능 시간 이후에는 직접 취소를 제한합니다.
**협의:** 사용자에게도 인원 선택형 부분취소를 제공할지는 D-03에서 확정합니다. 관리자 인원별 취소·부분환불 기능은 반영 대상입니다.

### CAN-02. 관리자 개별·전체 취소 [반영]
**동작:** 권한 있는 관리자는 개별 티켓 1개, 일부 인원, 한 회차 예약 또는 해당 부서의 운영 취소 대상을 선택해 취소합니다. 운영사 사유의 취소는 사용자 취소 마감 이후에도 가능합니다.
**확인:** 주문에 다른 부서 상품이 함께 있어도 자신의 권한 밖 티켓을 취소할 수 없습니다. 취소 사유·처리자·시간·대상·금액을 남깁니다.

### CAN-03. 부분환불 금액과 티켓 갱신 [반영 / 계산 협의]
**동작:** 취소 대상 인원의 실제 결제 배분액을 기준으로 환불 금액을 계산하고 원 결제에 부분환불을 요청합니다. 완료 후 해당 개별 티켓을 무효화하고 사용자 묶음 티켓의 남은 인원을 갱신합니다.
**협의:** 할인 유지·재계산, 원 단위 배분, 취소 수수료와 운영사 취소 시 환불 기준은 D-04에서 결정합니다. 정책 확정 전 임의의 공식을 고정하지 않습니다.

### CAN-04. 취소·환불 실패 및 이력 [설계안]
**동작:** 취소 요청, 처리 중, 환불 완료, 실패·확인 필요를 구분합니다. 외부 응답이 불명확하면 조회·재처리로 대조하며, 같은 취소 요청으로 두 번 환불하지 않습니다.
**확인:** 환불 금액은 남은 결제금액을 초과할 수 없습니다. 티켓 무효화·정원 복구 시점과 처리 중 입장 제한은 D-06에서 확정합니다.

### 동작 예시
포니 타기 10:00 회차를 3명 예약한 경우, 사용자는 3명짜리 티켓 1장, 관리자는 1명짜리 티켓 3개를 봅니다. 관리자 티켓 1개를 취소·환불 완료하면 사용자는 2명으로 갱신된 티켓을 보고, 나머지 2개의 관리자 티켓은 유지됩니다. 유효 인원이 남으므로 같은 시간에 다른 상품을 새로 예약할 수 없습니다.

## 07. 관리자 권한과 프로그램 운영
### ADM-01. 지역·부서·프로그램 권한 [반영 / 범위 협의]
지역 → 부서 → 프로그램 관계로 데이터를 관리합니다. 다른 부서 프로그램을 조회하는 것과 예약자 개인정보·결제 내역을 조회하는 것은 별도 권한으로 구분해야 합니다.

| 역할 | 기본 조회·처리 | 제한 및 확인 사항 |
| --- | --- | --- |
| 예약 회원 | 본인 장바구니·예약·티켓·취소 | 타인 예약 접근 불가 |
| 부서 담당 관리자 | 소속 프로그램 설정·예약·개별 취소 | 다른 부서 수정·삭제·취소 불가 |
| 타 부서 조회 권한 | 다른 부서 프로그램 조회 | 개인정보·매출 열람 범위 D-08 협의 |
| 전체 관리 역할 | 전체 조직·권한 관리가 필요한 역할 | 역할 신설 및 위이 운영 권한 D-08 협의 |

### ADM-02. 상품 및 판매 상태 관리 [반영]
**동작:** 상품 정보와 활성·비활성, 판매중·품절, 운영 기간 외·현장 예약만 가능 상태를 구분합니다. 품절은 미노출과 다르게 처리합니다.
**확인:** 비활성화해도 기존 예약·결제 이력은 삭제하지 않습니다. 예약이 있는 상품의 변경·삭제 허용 범위는 기획 단계에서 정합니다.

### ADM-03. 운영일·예약 기간·회차 설정 [반영]
**동작:** 상품별 운영일, 예약 오픈 범위, 이용일, 회차 시작·종료 시각, 판매 수량을 관리합니다. 모든 상품을 ‘향후 2주’로 고정하지 않습니다.
**확인:** 이미 판매된 회차의 시간·정원 변경은 기존 예약에 영향을 주므로 변경 대상·안내·취소 처리 기준을 확인한 뒤 적용합니다.

### ADM-04. 온라인 수량·할인·취소 정책 [반영]
**동작:** 온라인 판매 수량 또는 쿼터, 할인 대상·적용 수량, 사용자 취소 가능 시간을 설정합니다. 키오스크 수량과 자동 동기화하지 않습니다.
**확인:** 취소분은 확정된 복구 기준에 따라 재판매 가능 수량에 반영합니다. 두 상품이 같은 자원을 공유할 때 정원을 합산할지는 D-06에서 정합니다.

## 08. 예약 운영·매출·정산·인프라
### ADM-05. 예약·티켓 조회 및 운영 취소 [반영]

**확인:** 일괄 작업의 성공·실패·미처리 결과를 개별 예약 단위로 확인할 수 있어야 합니다.

**협의:** 결제일/이용일 기준, 환불 귀속 월, 수수료 배분 및 반올림 기준은 D-10에서 정합니다.

**동작:** 고객사가 제공하는 정산 양식에 맞춰 조회 결과와 예약·결제·환불 근거를 다운로드합니다. 화면 집계와 내려받은 자료가 일치해야 합니다.
**확인:** 자동 송금은 이 기능에 포함하지 않습니다. 자료의 개인정보 항목과 다운로드 권한은 D-08에서 확정합니다.

### OPS-01. 외부 서버·DB·도메인 운영 [반영]
**동작:** 위이가 외부 서버·DB를 구축·운영하고 마사회 구매 도메인을 적용합니다. HTTPS, 접근 통제, 백업·모니터링 등 운영 구성을 제공합니다.
**협의:** 세부 구성과 비용은 견적서를 따르며, 공공기관 보안 요건·개인정보 처리 기준은 D-13에서 확인합니다.

**동작:** 준비된 지역·부서·상품부터 오픈하고 미오픈 상품은 운영 안내를 표시합니다. 개발 완료와 실서비스 개시를 구분하며, 통합 QA와 고객사 검수 후 공개합니다.
**협의:** 회의의 추석 전 개발 목표·10월 오픈 의견·10월 16일 관련 일정은 확정 납기가 아닙니다. D-14에서 최종 대상을 포함해 확정합니다.

## 09. 주문·예약·티켓 데이터 구조
아래는 인원별 취소와 회차별 사용자 티켓을 함께 지원하기 위한 논리 구조입니다. 실제 DB 테이블·API 형식은 개발 설계에서 확정합니다.

| 관리 단위 | 관계 | 주요 관리 정보 |
| --- | --- | --- |
| 통합 회원 | 회원 1명 : 여러 주문 | 인증된 회원 ID, 로그인 연결 |
| 주문·결제 | 주문 1건 : 여러 예약 항목 | 공통 주문번호, PG 거래, 총액·환불 누계 |
| 회차별 예약 항목 | 상품·이용일·회차별 | 예약번호, 부서, 인원, 가격·할인 적용 내역 |
| 사용자 묶음 티켓 | 예약 항목 1건 : 표시 1장 | 유효 인원, 일정, 입장·취소 상태 |
| 관리자 개별 티켓 | 예약 인원만큼 생성 | 개별 티켓 ID, 배분 결제액, 취소·환불 상태 |
| 취소·환불 이력 | 취소 요청 : 대상 티켓들 | 사유, 처리자, 대상, 금액, PG 결과·처리 시각 |

### 필수 연결 관계 [설계안]
**회원 → 주문 → 회차별 예약 → 인원별 티켓** 관계를 유지합니다. 사용자 묶음 티켓은 이 예약의 유효 인원 합계를 보여줍니다. 관리자 티켓과 사용자 티켓이 서로 다른 예약 데이터를 중복으로 갖지 않도록 연결합니다.

### 상태를 구분해 관리
- **주문·결제 상태:** 결제 대기 / 결제 완료 / 결제 실패 / 부분환불 / 전체환불 등.
- **예약·개별 티켓 상태:** 예약 유효 / 취소 처리 중 / 취소 완료 등.
- **시간상 입장 상태:** 입장 대기 / 입장 가능 / 입장 종료. 취소된 티켓은 입장 불가.
- **환불 상태:** 요청 / 처리 중 / 완료 / 실패·확인 필요. 단순 화면 닫기를 처리 실패로 단정하지 않습니다.

### 금액·인원 정합성
유효 인원은 취소 완료된 개별 티켓을 제외하여 계산합니다. 개별 티켓의 배분 결제액 합계는 해당 예약 금액과 같아야 하며, 주문 전체의 환불 누계는 원 승인금액을 넘을 수 없습니다. 결제·취소 확정 단계의 동시 처리와 재요청 방지 방식은 서버에서 보장합니다.

| AT-03 | 서로 다른 상품·비중복 회차 담기 | 장바구니 항목 분리, 할인·총액 합산 |
| AT-04 | 같은 회원의 동일·부분 중복 시간 선택 | 상품·인원 수에 관계없이 차단 |
| AT-05 | 로그아웃 상태에서 선택 후 로그인 | 로그인 계정의 전체 예약과 다시 검사 |
| AT-06 | 다른 회원으로 변경 | 장바구니·예약 분리, 타인 정보 접근 불가 |
| AT-07 | 결제 중 정원·금액·예약 상태 변경 | 최신 서버 데이터로 재검증, 중복 판매 방지 |
| AT-08 | 결제 실패·중복 요청·결과 응답 지연 | 중복 청구/발급 없음, 확인 가능한 처리 상태 유지 |
| AT-09 | 한 회차 3명 및 다른 회차 1명 결제 | 사용자 티켓 2장, 관리자 개별 티켓 총 4개 |
| AT-10 | 3명 중 1명 부분취소 | 해당 인원만 무효화·환불, 남은 인원 2명 표시 |
| AT-11 | 부분취소 후 동일 시간 새 예약 | 남은 유효 인원이 있으면 계속 중복 차단 |
| AT-12 | 취소 마감 후 사용자/관리자 취소 | 사용자 제한, 운영사 사유의 권한 있는 관리자 취소 허용 |
| AT-13 | 타 부서 관리자 수정·취소 요청 | 화면뿐 아니라 서버에서도 권한 차단 |
| AT-14 | 환불 실패·재요청 및 정산 다운로드 | 중복환불 방지, 상태/이력 보존, 집계와 자료 일치 |
