이 문서는 이미 화면에 반영된 정책과 실제 개발·운영에서 더 확인할 일을 나눠 기록한다. 최신 화면의 입력·안내·동작을 기존 논의보다 우선한다. 현재 기능을 다시 미정으로 돌리거나, 서버 연동 요구를 구현 완료로 표시하지 않는다.

## 1 개발 착수 기준

현재 반영된 기준은 다른 프로그램 간 시간 중복 제한, 동일 이용일·지역·부서의 일괄결제, 1명 장바구니 카드, 사전 재고 선점 없음, 사용자 직접 부분취소, 유형별 고정 관리자 권한, 서비스 완료월 기준 익월 8일 정산과 PG 수수료 2%다. 이 항목은 기능명세의 D-01~D-14 현황표를 따른다.

착수 전에는 화면 내부 차이 S-01~S-05와 실제 PG·서버 실패 복구, 현장 입장·증빙, 개인정보·오픈 조건을 검토한다. 이전 문서의 시간 중복 차단·장바구니 수량 증감·혼합 부서 주문 제안은 현행 정책에서 제외했다.

## 2 예약과 티켓 및 결제의 관리 단위

한 결제에는 예약번호 하나를 발급한다. 신규 담기 N명은 1명 카드 N개이며 결제 후 카드별 하위 티켓을 생성한다. 사용자 목록은 예약번호로 묶고 관리자는 인원별 식별자로 취소 대상을 구분한다. 상품별 예약번호 -1·-2는 사용하지 않는다.

같은 회차를 한 사용자 티켓으로 합친다는 설명과 실제 카드별 생성은 S-02로 분리한다. 기존 복수 인원 예시 데이터는 신규 주문 단위의 근거로 삼지 않는다. 실명·생년월일 수집, 결제 후 기존 예약의 직접 회차 변경·인원 수정은 현재 제공된 것으로 가정하지 않는다. 한도 내 같은 회차 추가 구매는 새 주문으로 가능하다.

개발팀은 예약·인원별 티켓·결제·환불 식별자, 구매 당시 스냅샷, 배분 금액과 상태 관계를 설계한다.

## 3 구매 한도와 정원 경쟁 처리

다른 프로그램의 회차가 동일 계정의 기존 유효 예약 또는 장바구니와 이용 시간이 겹치면 차단한다. 같은 프로그램의 같은 회차는 재고와 구매 한도 안에서 여러 매 구매할 수 있다. 종료 시각과 다음 시작 시각이 같으면 허용하며 이동·준비시간은 추가하지 않는다. 프로그램별로 계정당 이용일별 최대 구매 수량을 설정한다(기본 4매). 같은 프로그램·이용일의 모든 회차·주문에 대해 기존 유효 예약과 장바구니 수량을 합산하고 취소 완료 수량은 제외한다. 다른 프로그램의 구매 수량은 합산하지 않는다. 과천시민 할인은 50%·이용일당 2매이며 프로그램·주문 간 합산한다. 취소 완료는 제외하고 남은 유효 인원만 계산한다.

| 상황 | 기대 결과 | 개발 확인 |
| --- | --- | --- |
| 두 회원이 마지막 한 자리 동시 결제 | 정원 내 한 명만 확정 | 서버 원자적 재고 처리 |
| 같은 계정이 두 기기로 겹치는 회차 결제 | 재고·하루 한도 내이면 허용 | 계정 수량 한도 초과 방지 |
| 같은 계정이 두 기기로 남은 한도 동시 사용 | 합산 한도까지만 확정 | 계정별 수량 경쟁 처리 |
| 두 프로그램의 같은 시간 판매 | 현재 프로그램별 독립 수량 | 현장 자원 공유는 운영 수량으로 관리 |
| 온라인과 현장 판매 | 별도 수량 | 키오스크 API 연동 없음 |

## 4 장바구니와 결제 중 재고

장바구니·결제 진입에서 좌석을 선점하지 않고 결제 확정 시 재고를 확인한다. 장바구니에서 인원 증감은 없고 1명 카드별 삭제만 제공한다. 다른 이용일·지역·부서는 함께 담지 못한다.

남은 개발 질문은 PG 승인과 재고 확정을 어떻게 일관되게 처리하는지다. 일부 회차가 마감되면 가능한 항목만 임의 결제하지 않는다. 승인 후 재고 확보 실패·저장 실패·응답 지연은 거래 조회를 통해 복구 또는 원 승인 취소를 추적해야 한다. 사전 선점 시간을 임의로 도입하지 않는다.

## 5 결제 성공과 예약 저장의 일치

실제 흐름은 서버 검증, 결제 시도 기록, 카드 결제 승인 확인, 예약·티켓 저장, 결과 조회가 일치해야 한다. 화면의 모의 완료만으로 실결제 성공을 판단하지 않는다.

| 상황 | 구현 요구 |
| --- | --- |
| 결제 버튼 반복·새로고침·중복 통지 | 한 요청은 한 번만 청구·발급 |
| 승인 후 완료 화면 이탈 | 예약 내역에서 결과 확인 |
| 승인 응답 지연 | 재조회 후 판단, 즉시 새 결제로 유도하지 않음 |
| 승인 성공·예약 저장 실패 | 예약 복구 또는 승인 취소와 담당·처리 기한 추적 |
| 뒤늦은 통지 | 확정 결과를 과거 상태로 되돌리지 않음 |

실제 PG 계약·지원 카드·부분취소·거래 조회·통지 검증을 확인한다. 포트원 거래번호 표시나 예시 기술키가 특정 PG 계약 확정을 뜻하지 않는다. 고객 자동 알림 미발송과 PG 서버 통지는 다른 기능이다.

## 6 부분취소와 환불

사용자 직접 인원 선택 취소는 제공한다. 환불 예정액은 선택한 티켓의 저장된 결제 배분액 합계이고 남은 티켓의 할인을 재계산하지 않는다. 현재 화면은 별도 고객 취소수수료를 차감하지 않는다. 취소 완료 수량만 구매 한도에서 제외한다.

예를 들어 정상가 5000원 티켓과 과천시민 50% 할인 2500원 티켓을 구매했다면 할인 티켓 취소 예정액은 2500원이고 정상가 티켓은 유지한다. 실제 PG 부분취소 제약은 별도 검증한다.

현재 예약 배지는 확정·부분 취소·취소 완료다. PG 환불 요청·결과 불명확·실패·재처리는 별도 거래 처리 상태로 설계한다. 결과 불명확 시 중복 환불하거나 재판매하지 않으며, 운영상 서비스 불가로 이미 휴장한 경우의 예약 상태와 환불 재처리는 구분해야 한다.

취소 마감 10분 안내와 입장 대기 조건의 차이는 S-01, 할인 복원 설정 전달 차이는 S-03이다. 이미 사용한 티켓·부분 입장·증빙 실패의 예외 환불은 현장 운영과 추가 확인한다.

## 7 입장 확인과 현장 운영

현재 티켓은 기본 20분 전부터 시간에 따라 입장 가능으로 표시하고 움직이는 표현과 증빙 안내를 제공한다. 실제 사용 완료·QR·직원 검표 기록이 있는 것으로 간주하지 않는다.

추가 결정은 나눠 입장 허용, 검표 방법, 잘못된 사용 처리 복구, 증빙 미제출 시 거절·차액·환불, 노쇼, 통신 장애 시 현장 대체 절차다. QR·오프라인·차액 결제 개발은 승인 없이 포함하지 않는다.

## 8 계정과 권한

통합 관리자는 전체 지역·부서와 계정 관리, 부서 공용 관리자는 자기 부서 업무 관리와 타 부서 프로그램 조회를 한다. 기능별 권한 부여·해제 설정은 현재 범위에 없다. 계정 삭제 제한은 연결 프로그램·업무 이력 기준이며 통합 관리자는 삭제하지 못한다.

서버는 본인 예약과 담당 부서 범위를 모든 요청에서 검증하고 삭제된 계정의 세션을 만료해야 한다. 비밀번호는 해시로 저장하며 분실 시 재발급한다. 공용 계정에서는 계정 ID·지역·부서·시각·사유를 남기고 개인 작업자를 식별한 것처럼 표현하지 않는다. 개인정보 마스킹·다운로드 감사·세션 만료는 운영 검수 항목이다.

## 9 운영값 변경과 과거 예약

프로그램 대표 이미지·요약 안내·이용 전 확인사항은 관리 입력 범위다. 예약 가능 일수는 프로그램별 N일이며 기본 14일이다. 별도 예약 판매 시작·종료일 필드를 가정하지 않는다. 운영 기간·요일, 노출 기간과 예약 가능 N일을 구분한다.

가격·할인·회차·입장 및 취소 설정 변경은 구매 당시 스냅샷과 구분한다. 과거 구매금액을 새 가격으로 바꾸지 않는다. 정원을 기존 예약 수 아래로 낮추지 못한다. 숨김·마감·휴장·삭제는 신규 판매와 이력 보존에 미치는 영향을 구분한다.

휴장 확인은 기존 예약 유지와 전체 취소·환불 중 하나를 선택한다. 유지하면 신규 예약만 중단하고, 취소 선택은 이미 환불한 금액을 제외한 유효 대상만 처리한다. 자동 고객 알림은 발송하지 않는다.

## 10 정산과 PG 전환

정산 기준은 실제 서비스 완료월이며 익월 8일 지급 예정이다. 승인 거래 2%를 수수료로 반영하고 취소는 취소액의 2%를 음수 조정한다. 미이용·완료 전 전액취소는 제외하고 완료 전 부분취소를 반영한다. 원장 묶음 행·원본 거래·엑셀 3개 시트는 같은 필터와 산식을 사용한다.

남은 확인은 세금계산서·선지급, 완료 후 예외 환불의 소급 또는 차월 차감, 부서별 정산 통장, 장기 PG 전환 시점과 과거 거래 환불이다. 실제 자동 송금은 현재 기능이 아니다. 부서 혼합 주문은 현재 차단되므로 이를 전제로 정산을 설계하지 않는다.

## 11 오류와 알림 및 운영 품질

| 상황 | 사용자 안내와 결과 |
| --- | --- |
| 다른 이용일·지역·부서 담기 | 기존 장바구니 결제 또는 비우기 안내 |
| 구매·할인 한도 초과 | 한도 사유 표시, 기존 카드 보존 |
| 회차 마감 | 일정 재선택, 임의 상품 대체 없음 |
| 금액 변경 | 변경 전후 확인과 동의 필요 |
| 결제·환불 결과 불명확 | 거래 재조회·복구 경로 제공 필요 |

다른 프로그램 간 시간 겹침은 구매 제한 오류다. 고객 자동 알림은 현재 미발송이므로 운영 취소의 현장 연락 절차와 향후 채널 도입을 별도로 정한다. 연락 실패를 예약 자동취소로 처리하지 않는다.

개인정보 수집·보관·삭제·탈퇴, 백업 복구 목표, 장애 담당, 오픈 예상 트래픽·지원 기기·접근성 기준은 운영 담당과 확인한다. 실제 개인정보·결제키를 예시 데이터로 배포하지 않는다. 법적 보관 기간·확정 납기는 화면만으로 정하지 않는다.

| S-04 | 확인사항 내용이 있으면 체크 필수 | 확인 필수 설정값의 의미와 적용 |
| S-05 | 예약 배지 3종, PG 실패·처리 상태 별도 필요 | 외부 거래 상태와 예약 배지의 연결 |

기존 P-01~P-04의 추적 범위는 유지한다. P-01은 결제 후 일정 변경·인원 수정, P-02는 결제 실패 복구, P-03은 현장 입장·증빙·노쇼, P-04는 운영값 변경·정산·PG 전환이다. 구체적 정책은 기능명세 D-01~D-14의 현재 기준을 먼저 따른다.

결정 기록은 정책 ID, 현재 동작, 변경 내용, 담당자, 결정일, 적용일, 기존 예약 영향, 관련 화면, 검수 사례로 남긴다. 승인자를 임의로 지정하지 않는다.

## 13 전달과 검수 순서

1. 최신 요구사항·기능명세·IA를 기준으로 운영값과 잔여 D·S 항목을 확인한다.
2. 서버·PG·티켓·환불 데이터와 실패 복구 방식을 설계한다.
3. 화면·API 응답·권한·이력·정산의 기대 결과를 맞춘다.
4. 실제 테스트 PG와 서버에서 통합 검수하고 운영 절차·오픈 승인을 확인한다.

## 14 근거와 개정 이력

2026-09-16에 최신 루트 화면·처리 코드와 정책 차이표를 기준으로 개정했다. 기존 2026-08-28 검토안의 중복 시간 차단, 사용자 부분취소 미정, 장바구니 선점 제안, 권한·정산 미정 문구를 현행 기준으로 갱신했다. 기존 기능·D·P·X 식별자는 추적용으로 유지한다.

계약 금액·납기·세무·보관 기간은 이번 문서로 변경하거나 확정하지 않는다. 화면 내부 차이의 상세 근거는 화면 기준 정책 차이 정리 문서와 요구사항 11장에 기록한다.
