# 렛츠런파크 화면 기준 정책 차이 정리

작성일: 2026-09-16 · 로컬 작업 폴더의 최신 화면 기준

개정 상태: 요구사항·기능명세 v1.1(Markdown·Word)·개발검토 v1.1·전달 문서·README·IA v1.1(HTML·Markdown·SVG)에 반영했다. 아래 기존 내용 열은 변경 전 이력이며 현행 지침이 아니다. 화면 내부 S-01~S-05는 미해결로 유지한다.

## 0. 적용 기준과 읽는 순서

**현재 화면을 가장 먼저 보고, 기존 정책 문서를 화면에 맞춰 정리한다.** 과거 문서의 ‘확정’ 표기만으로 최신 화면을 이전 정책으로 되돌리지 않는다.

우선순위는 **현재 화면의 입력·안내·버튼 동작 → 화면에 연결된 정책 설명 → 기존 요구사항·기능명세·검토안**이다. 화면 안내와 실제 동작까지 서로 다르면 둘을 함께 기록하고, 어느 쪽도 임의로 최종 정책으로 만들지 않는다.

이번 대조는 루트 HTML, 화면 처리 코드와 기존 Markdown 문서를 읽고 관련 자동 검사를 실행한 결과다. 브라우저 수동 조작이나 실제 로그인·PG·서버 연동 검수 결과는 아니다. 화면에 없는 계약·회계·개인정보 보관·현장 운영 조건은 미정으로 유지한다.

| 순서 | 대상 문서 | 정리 목적 |
| --- | --- | --- |
| 1 | 요구사항 | 현재 화면과 다른 기본 정책을 먼저 식별 |
| 2 | 기능명세서 | 사용자·관리자 동작과 검수 기대 결과 정정 기준 정리 |
| 3 | 기획자 개발검토 | 이미 화면에 반영된 내용을 미정 목록에서 분리 |
| 4 | 프론트엔드·정산 전달 문서 | 개발 전달 기준과 표시 방식 확인 |
| 5 | IA | 이전 문서 때문에 남겨둔 정책 확인 항목 정리 |
| 6 | 화면 내부의 불일치 | 문서만으로 해소할 수 없는 동작·안내 차이 분리 |

아래 ‘정리 기준’은 개정 문서에 반영한 내용이다. 차이표는 변경 이력과 화면 내부 잔여 항목을 추적하는 문서로 유지한다. 화면 동작 코드는 이번 문서 개정에서 변경하지 않았다.

| R-10 | 7장: 같은 예약의 승인·취소를 별도 거래 행으로 관리 | 화면 원장은 예약번호별 한 행. 펼치면 승인·부분취소·전체취소 원본 이력 표시 | ‘화면 원장 묶음 행’과 ‘개별 거래 데이터/이력’을 구분하여 기술 |

**그대로 유지할 내용:** 동시간대 예약 허용, 포니 구매 한도 이용일 하루 4매, 과천시민 50% 할인 하루 2매, 결제당 예약번호 하나, 온라인·현장 재고 분리, 서비스 완료월 기준 익월 8일 지급, PG 수수료 2%.

화면 근거: [예약·장바구니 규칙](../booking-rules.js)의 `cartScopeError`, `purchaseLimitError`, `discountLimitError`, `buildOrder`; [프로그램 화면](../admin.html)의 `detail-image`, `detail-notice`, `detail-booking-window`; [계정 화면 처리](../account-admin.js)의 `renderFixedAccessPolicy`; [운영 처리](../admin.js)의 `requestOperationClosure`.

## 6. 화면 내부에서도 서로 다른 부분

이 항목은 ‘이전 문서를 최신 화면에 맞추기’만으로 해결되지 않는다. 현재 보이는 설명과 실제 처리 조건을 함께 기록한다. 이번 작업에서는 화면을 수정하지 않는다.

### S-01. 취소 마감 10분 안내와 입장 대기 조건

- 설정 화면: 기본 회차 시작 10분 전까지 사용자 취소 가능.
- 실제 버튼 조건: `ticketCanCancel`은 입장 대기 상태이면서 취소 마감 전인 경우만 허용.
- 기본 입장 가능 시작: 회차 시작 20분 전. 따라서 기본값에서는 시작 20분 전부터 이미 직접 취소 불가.
- 예: 10:00 회차는 설정상 09:50 마감이지만 실제로는 09:40부터 입장 가능 상태가 되어 취소 버튼이 막힘.
- 문서에는 두 조건을 모두 기록한다. ‘10분 전까지 항상 취소 가능’으로 단정하지 않는다.
- 근거: [app.js](../app.js)의 `ticketTiming`, `ticketCancellationDeadline`, `ticketCanCancel`, `renderTicketCancellation`; [admin.html](../admin.html)의 취소 설정 안내.

### S-02. 사용자 회차별 묶음 티켓 설명과 신규 생성 단위

- 화면 정책 설명은 상품·이용일·회차별 묶음 티켓 1장을 안내한다.
- 실제 신규 담기는 인원수만큼 1명 카드를 만들고, `buildOrder`는 카드별 하위 티켓을 생성한다.
- 사용자 목록의 `ticketListGroups`는 예약번호 기준으로 그룹을 만들지만 같은 회차의 하위 티켓을 다시 합치지는 않는다.
- 예시 데이터는 한 티켓에 2명인 경우도 있어, 예시 화면만 보면 신규 주문과 다른 단위를 보게 된다.
- 현행 동작을 기록할 때는 ‘예약번호 묶음 안에 카드별 티켓’으로 설명한다. 회차별 재병합을 구현된 기능으로 쓰지 않는다.
- 근거: [app.js](../app.js)의 `addToCart`, `defaultTicketReservations`, `ticketListGroups`; [booking-rules.js](../booking-rules.js)의 `buildOrder`; [화면 정책](../developer-policy.js)의 티켓 표시 단위.

### S-03. 할인 한도·복원 설정과 사용자 계산의 연결

- 관리자 화면은 주문별·계정/이용일별·계정 전체 기간·수량 제한 없음과 취소 시 복원 여부를 설정한다.
- 사용자 프로그램으로 할인 정보를 옮기는 코드는 `maxQtyPerDate`를 기준으로 만들며 `scope`·`restoreOnCancel`을 그대로 전달하지 않는다.
- 사용자 할인 집계는 취소 완료 인원을 제외한 유효 수량을 이용일별로 합산한다.
- 따라서 관리자에 설정 UI가 있다는 이유만으로 모든 집계 방식·복원 OFF가 사용자 흐름에 적용됐다고 쓰지 않는다. 화면 설정 범위와 실제 적용 범위를 구분한다.
- 근거: [admin.js](../admin.js)의 `discountScopeText` 및 할인 저장; [app.js](../app.js)의 할인 정책 변환; [booking-rules.js](../booking-rules.js)의 `discountLimitError`.

### S-04. 이용 전 확인사항의 확인 필수 여부

- 프로그램 데이터에는 `requiresGuidanceConfirmation` 설정이 있다.
- 실제 사용자 화면은 확인사항 텍스트가 있으면 확인 체크를 보여주고, 미체크 시 예약 진행을 막는다. 해당 조건은 위 설정값을 검사하지 않는다.
- 현행은 ‘내용이 있으면 확인 필수’로 기록한다. 설정 ON/OFF에 따라 선택 확인으로 바뀐다고 명세하지 않는다.
- 근거: [app.js](../app.js)의 `bookingSelectionError`, `renderProgramGuidance`.

### S-05. 예약 상태와 외부 결제·환불 처리 상태

- 관리자 예약 상태는 예약 확정·부분 취소·취소 완료를 사용한다.
- 개발 검토안의 환불 요청·처리 중·실패·확인 필요는 외부 PG 연동을 위한 별도 설계안이다.
- 현재 예약 목록에 처리 중 배지가 있는 것으로 기술하지 않는다. 반대로 예약 상태가 3개라고 서버 환불 실패 기록까지 없애는 것으로 해석하지 않는다.
- 근거: [developer-policy.js](../developer-policy.js)의 예약 상태 값, 부분취소·부분환불 설명. 실제 PG 실패 흐름은 아직 통합 검수 대상이다.

## 7. 원문 개정 이력

1. **요구사항 개정 완료:** R-01~R-11을 반영하고 S-01~S-05를 별도 장에 기록했다.
2. **기능명세서 개정 완료:** F-01~F-16과 AT 기대 결과를 수정하고 기존 기능 ID 27개를 유지했다. AT-15~AT-19로 장바구니·휴장·정산 사례를 보완했다.
3. **개발 검토안 갱신 완료:** P-01~P-10을 현재 반영 사항으로 옮기고 실제 서버·PG·현장 운영 확인 사항을 분리했다.
4. **전달 문서·IA 동기화 완료:** H·I 항목을 반영하고 IA 생성 원본에서 HTML·Markdown·SVG를 다시 생성했다. 37개 항목과 기존 메뉴 구조를 유지했다.
5. **Word 배포본 동기화 완료:** 기능명세 DOCX를 같은 v1.1 본문으로 갱신했다. 견적서의 금액·계약 내용은 이번 정책 문서 개정으로 변경하지 않았다.
6. **S-01~S-05는 별도 동작 정리:** 이미 확인된 화면 내부 차이이므로 문서 수정만으로 해소 완료 처리하지 않음.
